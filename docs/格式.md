# kagi 库格式（第 1 版）

这份文档写给要独立实现 kagi 格式的人，包括 kagi 坏了之后的你自己。照着它，不看 kagi 的源码也能解开库。`recover/recover.swift` 就是只照着这份文档写的。

## 用到的算法

kagi 不自己设计算法，只组合下面这些标准件，全部由 CryptoKit 提供：

| 用途 | 算法 |
|---|---|
| 加密每条值、元数据、恢复包装 | AES-256-GCM，12 字节 nonce，16 字节 tag |
| 把库内密钥包给设备 | HPKE（RFC 9180）base 模式，套件 DHKEM(P-256, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM |
| 从恢复密钥派生加密密钥 | HKDF-SHA256 |
| 密钥校验值 | HMAC-SHA256 |
| 恢复密钥的校验位 | SHA-256 |

约定：
- 文中的「Base64」都是标准 Base64，带 `=` 填充。
- 「绑定串」是 UTF-8 字符串，用作 AES-GCM 的附加数据（AAD），也用作 HPKE 的 info 和 AAD。

AES-GCM 的结果统一存成 `Base64(nonce ‖ 密文 ‖ tag)`，也就是 CryptoKit 的 `AES.GCM.SealedBox.combined`。

## 两把库内密钥

每个库有两把随机生成的 256 位对称密钥：

- **库密钥**（secret）：加密每一条值。用它的设备密钥要求按指纹。
- **索引密钥**（index）：加密名字和元数据。用它的设备密钥不要求按指纹，所以 `kagi ls` 不弹框。

## 文件夹结构

```
<库>/
  vault.json
  keys/
    <设备 ID>.json
    recovery.json
  entries/
    <条目 ID>/
      0001.kagi
      0002.kagi
  index/
    <条目 ID>.kagi
```

- 库 ID：16 字节随机数，用小写 Crockford Base32 写出（26 个字符）。界面上只显示前 4 个字符，比如 `k-8mxh`。
- 条目 ID：10 字节随机数，小写 Crockford Base32（16 个字符）。
- 设备 ID：`mac-` 加上 5 字节随机数的小写 Crockford Base32。
- 版本号从 1 开始，文件名补零到 4 位：`0001.kagi`。每改一次就写一个新文件，旧文件不删。
- 所有 `.json` 和 `.kagi` 文件的内容都是 JSON，时间写成 UTC 的 ISO 8601（比如 `2026-10-25T12:54:49Z`）。

## vault.json

```json
{
  "format": "kagi-vault/1",
  "vault": "<库 ID>",
  "created": "<时间>",
  "keyCheck": "Base64(HMAC-SHA256(库密钥, \"kagi-key-check/1|<库 ID>|secret\"))",
  "indexKeyCheck": "Base64(HMAC-SHA256(索引密钥, \"kagi-key-check/1|<库 ID>|index\"))"
}
```

每台设备加入库时，都会把这两个校验值记在本机，然后每次打开库都拿 vault.json 来比对。网盘上有人换了钥匙或改了校验值，这一步就能发现。

## keys/<设备 ID>.json

```json
{
  "format": "kagi-device/1",
  "vault": "<库 ID>",
  "device": "<设备 ID>",
  "name": "<电脑名>",
  "created": "<时间>",
  "secretPublicKey": "Base64(设备密钥 A 的公钥，X9.63 非压缩格式)",
  "indexPublicKey": "Base64(设备密钥 B 的公钥)",
  "secretWrap": { "enc": "Base64(HPKE 封装的密钥)", "ciphertext": "Base64(HPKE 密文)" },
  "indexWrap": { "enc": "…", "ciphertext": "…" }
}
```

- 设备密钥 A、B 都是这台 Mac 的 Secure Enclave 里的 P-256 密钥，只能在这台设备上用。
  - A 的访问控制是「使用时要按指纹或输登录密码」。
  - B 不要求验证，但屏幕解锁时才能用。
- `secretWrap`：用 A 的公钥做 HPKE，封装的明文是库密钥的 32 个字节。info 和 AAD 都是 `kagi-device/1|<库 ID>|<设备 ID>|secret`。
- `indexWrap`：用 B 的公钥封装索引密钥。info 和 AAD 是 `kagi-device/1|<库 ID>|<设备 ID>|index`。

## keys/recovery.json

```json
{
  "format": "kagi-recovery/1",
  "vault": "<库 ID>",
  "secretWrap": "Base64(AES-GCM(加密密钥, 库密钥, AAD = \"kagi-recovery/1|<库 ID>|secret\"))",
  "indexWrap": "Base64(AES-GCM(加密密钥, 索引密钥, AAD = \"kagi-recovery/1|<库 ID>|index\"))"
}
```

### 恢复密钥

- 先生成 18 字节随机数 `s`。
- 校验位是 `SHA-256("kagi-recovery-checksum/1" ‖ s)` 的前 2 个字节。
- 把 `s ‖ 校验位` 一共 20 字节写成 Crockford Base32，正好 32 个字符，分成 8 组、每组 4 个，用 `-` 连接。
- 字母表是 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`。解码时忽略大小写、横线和空格，把 O 当 0，I 和 L 当 1。

加密密钥 = HKDF-SHA256：
- 输入密钥材料是 `s`
- 盐是 `"kagi-recovery/1|<库 ID>"`
- info 是 `"kagi recovery key-encryption key"`
- 输出 32 字节

## entries/<条目 ID>/<版本>.kagi

```json
{
  "format": "kagi-entry/1",
  "vault": "<库 ID>",
  "entry": "<条目 ID>",
  "version": 2,
  "created": "<时间>",
  "box": "Base64(AES-GCM(库密钥, 明文, AAD))"
}
```

- AAD 是 `kagi-entry/1|<库 ID>|<条目 ID>|<版本>|<created>`。文件被挪到别的条目或版本下面，或者时间被改过，都会解密失败。
- 明文是 JSON：`{"ref": "<引用>", "value": "Base64(值的原始字节)"}`。解出来以后，还要核对 `ref` 和索引里的名字是否一致。

## index/<条目 ID>.kagi

```json
{
  "format": "kagi-index/1",
  "vault": "<库 ID>",
  "entry": "<条目 ID>",
  "box": "Base64(AES-GCM(索引密钥, 明文, AAD = \"kagi-index/1|<库 ID>|<条目 ID>\"))"
}
```

明文是 JSON：

```json
{
  "ref": "resend/api-key",
  "issuer": "Resend",
  "usedIn": "Kotolog 生产：Railway、Vercel",
  "created": "<时间>",
  "updated": "<时间>",
  "latestVersion": 2
}
```

`issuer` 和 `usedIn` 可以没有。读值时，以 `entries/<条目 ID>/` 里版本号最大的文件为准，`latestVersion` 用于显示并检查索引与条目是否一致；不一致时停止操作，确认同步完成后可用 `kagi repair-index` 重建索引。

## 引用

引用由一段或多段组成，段与段之间用 `/` 分开，比如 `resend/api-key`。

每一段的规则：
- 只能用小写字母、数字和 `.` `_` `-`；
- 必须以小写字母或数字开头；
- 不超过 64 个字符。

整个引用不超过 200 个字符。

## 这台 Mac 自己的文件（不进网盘）

放在 `~/Library/Application Support/kagi/` 下面，目录权限 0700，文件权限 0600：

- `device.json`：库的位置、库 ID、设备 ID、记下的两个校验值，以及两把 Secure Enclave 密钥的 blob。这些 blob 只有在这台 Mac 的 Secure Enclave 里才用得了。
- `log.jsonl`：使用记录，一行一条 JSON，不含任何值。

## 不经过 kagi 怎么解开库

1. 读 `vault.json` 拿到库 ID；读 `keys/recovery.json`。
2. 按上面的规则解码恢复密钥，核对校验位，派生加密密钥。
3. 用加密密钥解开 `secretWrap`，得到库密钥。
4. 对每个 `entries/<条目 ID>/`，取版本号最大的文件，用库密钥解开，得到 `ref` 和值。

`swift recover/recover.swift --vault <库> --out <输出文件夹>` 做的就是这几步。

## 写入与修复

本机通过隐藏的 `.write.lock` 文件协调写入；它不属于加密格式，也不能协调不同设备。版本密文先完整写入同目录的隐藏临时文件，再通过 macOS 排他重命名发布，已有目标不覆盖。索引随后原子替换；两者不是一个事务。索引缺失或版本不一致时，正常操作会报错。

`kagi repair-index` 要求用户验证，先认证解密所有条目的最新版本，检查引用唯一且不落后于已有索引，再写索引。保留现存索引里的签发方、用途和创建时间；丢失索引时只能恢复引用、条目时间和版本。修复中断可重跑；它不删除版本、处理重复引用或替用户选择同步冲突。设备之间应串行写入并等待同步，静默同版本覆盖不保证检出。

独立恢复脚本先验证全部条目，再导出到 `<输出目录>/<条目 ID>/<引用最后一段>`。文件名不自动加扩展名，`manifest.json` 保存每条的 `ref` 与相对文件路径 `file`。每个条目使用独立目录，避免 `foo` 与 `foo.txt` 或引用前缀产生覆盖。导出文件以排他方式创建，权限 0600。

## Space 与 key 管理扩展

值文件 `kagi-entry/1`、库密钥和恢复包装保持原格式。新写入索引使用 `kagi-index/2`；读取同时支持 `/1` 和 `/2`。`/2` 的 AES-GCM AAD 为 `kagi-index/2|<库 ID>|<条目 ID>`。旧程序不接受 `/2`，避免覆盖索引时丢弃新字段。

索引明文原有字段保持不变，新增 `metadata`：

```json
{
  "title": "Resend 生产",
  "space": "kotolog",
  "tags": ["api", "prod"],
  "notes": "用途说明",
  "archived": false
}
```

`title` 和 `notes` 为可选字段；旧 `/1` 索引没有 `metadata` 时，默认 `space=default`、`tags=[]`、`archived=false`。Space ID 为引用规则的单段、不超过 64 字符。标签经 Unicode NFC 规范化、去除首尾空白、转小写，去重并按字典序排列；每条最多 32 个，每个不超过 64 字符。标题最多 120 字符，备注最多 4000 字符；控制字符不允许，备注可含换行和制表符。`issuer` 与 `usedIn` 保留在原位置。

每个 Vault 最多一个 `catalog.kagi`，它的 JSON 为：

```json
{
  "format": "kagi-catalog/1",
  "vault": "<库 ID>",
  "box": "Base64(nonce ‖ 密文 ‖ tag)"
}
```

使用索引密钥 AES-GCM 加密，AAD 为 `kagi-catalog/1|<库 ID>`。明文为 `{ "spaces": [{ "id": "default", "name": "默认", "created": "<时间>", "updated": "<时间>" }] }`。目录缺失表示只有默认 Space，其时间取 `vault.json.created`。目录存在时必须包含默认 Space；ID 唯一。标题与 Space 名称仅用于显示，引用始终全库唯一；移动 Space 不修改值文件或引用。归档保存在索引中，不删除值文件，也不构成加密撤销。

管理写入沿用本机写锁，key 更新要求提供读到的完整快照以检查并发修改。`Listing` 的 `revision` 是索引密文 box 的 SHA-256（标准 Base64），读取、写入和管理更新都比较此指纹；仅版本号和秒级时间戳相同不代表快照未变化。Space 操作原子替换目录文件；不提供跨设备事务或并发合并。删除 Space 前检查所有索引，包括归档条目。索引修复保留现存管理字段；无法恢复的字段采用默认值且强制 `archived=true`，避免意外重新启用之前归档的 key。独立恢复脚本仍恢复全部值文件，包括归档项，不恢复 Space 或标签信息。

## 验证器类型扩展

`IndexRecord.kind` 与值明文 `EntryPlain.kind` 均为 `secret`、`totp`、`passkey`。历史普通值没有此字段时默认为 `secret`。普通值继续写 `kagi-entry/1`、`kagi-index/2`；验证器值写 `kagi-entry/2`、索引写 `kagi-index/3`，对应 AAD 的首段必须使用各自完整格式名。原有格式与类型不得互相混用；读取还要核对加密值内部的 kind 与索引一致。

验证器值明文外层仍是 `{ref, value, kind}`，`value` 为下列内部 JSON 的 UTF-8 字节再做 Base64，外层由库密钥 AES-GCM 加密：

- TOTP：`{secret, algorithm, digits, period, issuer?, account?}`。secret 使用标准 Base64 保存字节，不是 RFC 4648 Base32 文本；algorithm 为 SHA1/SHA256/SHA512。
- Passkey：`{rpID, credentialID, userHandle, userName, privateKey}`。三个字节字段用标准 Base64；privateKey 为 CryptoKit P256.Signing 私钥的 32 字节 rawRepresentation。该密钥由 Vault 加密包装，不是 Secure Enclave 设备密钥。

索引只增加 kind，不包含上述内部值。更新管理信息保留 kind；修复从受认证的值明文恢复 kind，缺失管理字段仍先归档。旧客户端不支持验证器格式，不能用旧版修复工具重建或导出它们。新版独立恢复清单增加 `kind`，导出验证器内部 JSON；常规 `recover` 则保留原库全部字段。

TOTP 算法按 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) 和 [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226.html)，URI 按 [Google Key URI Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format)。Passkey 核心响应按 [WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) 的 ES256/COSE/none attestation 子集。此版本不提供完整 WebAuthn 客户端或系统提供者，也不接受完整浏览器 options。

## 独立同步仓库 v1

`SyncTransport` 与业务库分离，约定 `identity`、`head()`、`object(id)`、`put(bytes)`、`compareAndSwap(expected:replacement:)`。对象不可变，ID 为传输字节的 SHA-256；必须先持久化对象，再用服务端原子条件更新发布 HEAD。网络超时可留下未被 HEAD 引用的对象；不可把普通覆盖上传当 CAS。目录适配器用同文件系统的 flock 和原子写实现此约定，云服务适配器尚未实现。

目录仓库为 `<remote>/<vaultID>/HEAD` 与 `objects/<sha256>`，不与本地工作副本混用。HEAD 是 64 字符小写十六进制；对象为 JSON `kagi-sync-archive/1`：`{format,vault,recovery,box}`，其中 `vault` 与 `recovery` 为原有文件结构。AAD 是按当前 JSON 规则编码的 `{format,vault,recovery}`；box 使用库密钥 AES-256-GCM。解开后是 `{format:"kagi-sync/1",vault:<ID>,parents:[<对象ID>],files:{<相对路径>:<Base64字节>}}`。父节点最多两个。公开头必须与加密内容中的库头、恢复封装匹配。

快照只允许 vault.json、catalog.kagi、keys/*.json、index/*.kagi、entries/<ID>/<规范版本>.kagi。路径拒绝遍历、非规范版本号、符号链接和特殊文件；不发送本机 device.json 私钥 blob、日志、写锁或同步状态。空 entries/index 目录在安装时创建。每个候选快照在临时隔离目录验证库身份、Space、引用唯一性、索引/最新版本及全部历史值的 AEAD 和类型结构。

三方比较使用本机已确认基线、当前本机与远端。key 的索引和全部版本按 ref 作为一组，Space 按 ID 比较；其余库头与设备封装按文件比较。未改变侧接受改变侧；双方不同修改形成冲突。不存在跨字段的密钥自动拼接。Space 归属依赖冲突选择相关 Space 和 key 的同侧状态，禁止覆盖已明确提交的相反选择；依赖选择之间也必须一致。冲突 ID 是祖先与双方内容的规范 JSON SHA-256，只有本次冲突可使用对应选择。key ID 因同名 ref 分别创建而不同时，选择后仅保留一个当前 ID，双方原快照保留。

本机隐藏文件（不属于同步快照）：`.sync-state` 保存 transport identity 与已确认 revision；`.sync-conflicts` 保存双方 revision 与冲突列表；`.sync-pending` 保存安装目标与对应 revision。`.sync-retired/` 保存被替代条目遗留的未完成隐藏密文，不参与同步。均用库密钥加密，AAD 为 `kagi-sync-local/1|<vault>|state|conflicts|pending`（最后一段择一）。安装步骤：验证合并目标、发布不可变对象、CAS HEAD、持久化 pending、安装全部文件并删除被替代文件、持久化 state、清除 pending。中断后重放目标，普通操作检测 pending 并暂停。pending 和目标文件使用原子写与 fsync，新建目录、删除旧文件以及清除 pending 后同步持久化父目录；旧文件清理仅枚举安全路径，不将安装中的新旧文件并集计入单快照限制；被替代目录若仍有未完成隐藏密文，排他移动到 `.sync-retired/`，持久化双方父目录；不宣称外部云盘同步具有事务能力。

当前每份本地库绑定一个 transport identity。快照最多 10000 文件与 32 MiB 原始文件，单传输对象上限 64 MiB；祖先检查最多 4096 个对象、累计 256 MiB 输入。无远端对象删除、压缩、历史浏览或自动历史裁剪。未来提供者需保持本协议的不可变对象、身份稳定与条件更新语义。
